所有上过 C 语言课的人，一定都遇到过这道千年老题：下面这行的结果是多少？

```c
int i = 5;
i = i + (i++);
```

有人算 10，有人算 11，还有人搬出自己电脑上的运行结果来争论。但标准给出的答案是：**这是未定义行为（undefined behavior，UB）**——既不是 10，也不是 11，而是"没有规定"。

可是凭什么，计算机一个这么注重实践、“跑出来是什么就是什么”的学科，在这个问题上却变得有争议了呢？

## 目录

## 一、标准为什么说它是 UB

### 先看 UB 的定义

C11 标准 §3.4.3 给 UB 下的定义是：

> behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements

翻译过来：**当程序使用了不可移植的构造、错误的构造，或者错误的数据时，标准对这种行为不施加任何要求。**

关键词是 "no requirements"。标准没有说"程序必须崩溃"，也没有说"结果随机"，它说的是"我不再管了"。于是实现可以忽略这个操作、按平台习惯给出一个结果、在翻译期或运行期直接报错，甚至做一些看起来完全不讲道理的事——comp.std.c 上那个著名的说法是，UB 可以让"恶魔从你的鼻子里飞出来"。

它和另外两种"不确定"要区分开：

| 名称         | 谁决定                   | 例子                            |
| ------------ | ------------------------ | ------------------------------- |
| 实现定义行为 | 实现必须选一种并写进文档 | `char` 是否有符号；有符号数右移 |
| 未指定行为   | 实现自己挑，不必告诉你   | 函数参数的求值顺序              |
| 未定义行为   | 谁都不管                 | 有符号溢出、空指针解引用        |

前两者仍然是合法程序，只是结果不由标准钉死；UB 则是程序已经不在标准的保护范围里了。这个区别很重要：**"结果不确定"和"程序没有意义"是两回事。**

### 为什么这一行是 UB

具体到 `i = i + (i++)`，C11 标准 §6.5p2 写得很直接：

> If a side effect on a scalar object is unsequenced relative to either a different side effect on the same scalar object or a value computation using the value of the same scalar object, the behavior is undefined.

翻译一下：**如果对一个标量对象的副作用，和同一个对象上的另一个副作用（或一次取值）之间没有先后顺序，行为就是未定义的。**

把 `i = i + (i++)` 拆开看，`i` 在这条语句里出现了三次：

- `i++` 会**修改** `i`，这是副作用；
- 左边的 `i` 和 `i++` 里的 `i` 都要**读取** `i` 的值；
- 最外层的 `=` 又会**写入** `i`，这是第二个副作用。

问题在于，标准没有规定 `+` 的两个操作数谁先求值，也没有规定赋值和 `i++` 谁先发生。于是"读 `i`"和"改 `i`"之间没有任何顺序保证，正好撞上 §6.5p2——UB。

有人会问：这不算"求值顺序未指定"（unspecified behavior）吗？不算。未指定行为是指每一种顺序都能给出一个确定结果，只是标准不指定选哪个；而这里无论按哪种顺序执行，都会出现"读"和"写"交错，没有任何一种解释是自洽的，所以标准直接把它归为 UB。

BTW，C++17 通过 P0145 重新规定了赋值运算符的求值顺序，所以 `i = i++` 这种写法在 C++17 之后是良定义的。但 `i = i + (i++)` 不同：`+` 的两个操作数之间仍然是无序的，"读 `i`"和"改 `i`"的冲突还在，所以在 C++ 里它依然是 UB。编译器对此的警告也很能说明问题——`i = i++` 在 C++17 下不再报警告，而 `i = i + (i++)` 在 C++20 下依然会报 `unsequenced modification and access to 'i'`。换句话说，这不是"C++ 把它修好了"，只是修好了其中一部分。

## 二、编译器如何利用 UB

理解了定义，就能理解编译器为什么敢对 UB 代码"胡来"：因为编译器默认你的代码**不可能**存在 UB，所以可以由此做出激进的优化。

看一个比考试题更能说明问题的例子：

```c
int always_true(int x) {
  return x + 1 > x;
}
```

在我电脑上用 `Clang -O2` 实际编译：

```asm
always_true:
        movl    $1, %eax # eax 寄存器用于存放函数返回值
        retq
```

整个函数只剩"返回 1"两条指令，连 `x` 都没碰。

理由很直接：如果 `x == INT_MAX`，`x + 1` 就是有符号溢出，而 C 标准规定有符号溢出是 UB。既然这种输入"不可能发生"，那么 `x + 1 > x` 对编译器来说恒成立，索性直接返回 1。它不是算错了，而是根本没打算算：编译器只对不触发 UB 的输入负责，而在那些输入上，结果恒为 1。

这就是 UB 最反直觉的地方：**它不是"运行时会随机崩溃"，而是"编译器可以合法地假设它不会发生"，然后把这个假设传播到整个函数。** 本文开头那道题在 `-O0` 下可能输出 10，在 `-O2` 下可能输出 11，换台机器又可能变成别的数——这些结果都只是巧合，不构成任何证据。

## 三、还有哪些常见的 UB

UB 远不止自增这一种。按类别挑几个最常见的：

- **整数运算**：有符号溢出；左移负数；移位量大于等于类型的位宽；`INT_MIN / -1` 和 `abs(INT_MIN)`；浮点数转整数时超出目标范围。
- **内存访问**：解引用空指针；数组越界（读也算）；悬垂指针、use-after-free、重复 `free`；读取未初始化的局部变量；`memcpy` 的源和目标重叠。
- **指针与类型**：把 `float *` 强转成 `int *` 再解引用（违反严格别名）；用未对齐的指针访问要求对齐的类型；对不是数组元素的指针做越界算术。
- **求值顺序**：和开头那题同源的 `i++ + i++`、`a[i] = i++`、`printf("%d %d", i++, i++)`。
- **标准库**：`printf` 的格式串与参数类型不匹配；`toupper` / `tolower` 传入负的 `char`；修改字符串字面量。
- **并发**：两个线程无同步地访问同一块内存，且至少有一个在写——这就是数据竞争，而数据竞争是 UB。

顺带一提，并不是所有"看着危险"的写法都是 UB：`free(NULL)` 就是合法的，什么也不做。UB 的边界有时候和直觉并不一致，遇到拿不准的写法，查标准或者查 cppreference 比在机器上试要可靠得多。

更重要的是，上面这些写法里有很多在 `-O0` 下都能"正常"运行。这正是 UB 危险的地方：它平时不响，等到换了编译器、开了优化、换了机器，才一次性发作。

## Bonus Time：10 和 11 分别是怎么算出来的

这个板块是我出于私心加上的。第一次遇到开头那道题时，我并不知道这是 UB，但确实被它困扰过：从汇编的角度看，编译器既可以先把 i 的旧值读进寄存器、后面一直用这个旧值，也可以先做 i++、再让加法使用更新后的 i，两种顺序得到的结果自然不一样。

那不妨就来看看真实的汇编代码吧：

Clang（x86-64，`-O0`，AT&T）：

```asm
movl    $5, -4(%rbp)      # i = 5
movl    -4(%rbp), %eax    # eax = i（左操作数，5）
movl    -4(%rbp), %ecx    # ecx = i（i++ 的旧值，5）
movl    %ecx, %edx
addl    $1, %edx          # edx = 6
movl    %edx, -4(%rbp)    # i = 6
addl    %ecx, %eax        # eax = 5 + 5 = 10
movl    %eax, -4(%rbp)    # i = 10
```

关键在于 `addl %ecx, %eax`：加法用的是早就暂存在 `%ecx` 里的旧值 5，并没有回头去读内存。所以尽管 `i` 已经被写成 6，结果仍然是 10。

GCC（x86-64，`-O0`，AT&T）：

```asm
movl    $5, -4(%rbp)      # i = 5
movl    -4(%rbp), %eax    # eax = i（5），准备算 i++
leal    1(%rax), %edx     # edx = 6
movl    %edx, -4(%rbp)    # i = 6
addl    %eax, -4(%rbp)    # i = i + 5 = 6 + 5 = 11
```

GCC 先把 `i` 加一写回内存，再让 `addl` 直接对内存里的 `i` 做加法——这时它已经是 6，于是结果是 11。

同一份源码，编译器选哪条路径都不算违反标准，10 和 11 的差别就来自这里。

但是说真的，我并不理解，一道从根源上就是错误的题目，**凭什么**可以在题库里、在考试中存在十几年甚至几十年之久。这分明是一个崇尚严谨的学科，但在这么一道显然的错题上，却能够视而不见。

最重要的是，工程里没人这样子写代码，你敢这么写 ci lint 大概率会把你拦下来，哪怕真过了 ci，code review 时也会遭受同事的毒打。
