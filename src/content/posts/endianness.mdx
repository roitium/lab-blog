调试二进制协议的时候，经常会出现这种场面：抓包看到端口号是 `1f 90`，自己在代码里打印出来却是 `90 1f`；`fwrite` 存下来的结构体，换一台机器读出来全是乱的。这类问题的根子，大多指向同一个概念：字节序。

## 目录

## 什么是字节序

内存是按字节编址的，每个地址对应一个字节。但 `uint32_t`、`float`、`double` 这类类型有多个字节，CPU 必须决定：**一个多字节数据的几个字节，按什么顺序放进连续的内存地址里**。

这个顺序就是字节序（endianness）。它只对「大于一个字节」的数据有意义——`char`、`uint8_t`、UTF-8 文本、字节数组都不受它影响。

- **大端序（big-endian）**：最高有效字节 `0x12` 放在最低地址 `0x1000`，内存里读出来是 `12 34 56 78`，和书写顺序一致。
- **小端序（little-endian）**：最低有效字节 `0x78` 放在最低地址 `0x1000`，内存里读出来是 `78 56 34 12`，和书写顺序相反。

所以「大端 / 小端」说的是**字节**的排列，不是位的排列；`0x12345678` 这个数值本身没有变，变的只是它在内存里的落地方式。

## 为什么会有两种字节序

这更多是历史与工程取舍，而不是谁更「正确」。

- 小端序把低位字节放在低地址，做多字节加法时可以从低地址开始逐字节进位；把一个 32 位值截断成 16 位时，低半部分所在地址不变。早期一些 CPU 这样实现更省事。
- 大端序让内存里的字节顺序和数值的书写顺序一致，看 hexdump 时更符合直觉，网络协议因此选了它。

至于「哪种更快」，在现代 CPU 上基本没有差别，不要把它当成选型依据。

## 谁在用哪种

| 场景                    | 字节序                          |
| ----------------------- | ------------------------------- |
| x86 / x86-64            | 小端                            |
| ARM / AArch64           | 通常小端（架构本身支持双端）    |
| RISC-V                  | 小端                            |
| TCP/IP 等网络协议       | 大端（网络字节序）              |
| Java `.class`、Java NIO | 大端                            |
| PNG、JPEG               | 大端                            |
| BMP、GIF、ZIP           | 小端                            |
| ELF                     | 由头部 `EI_DATA` 字段标明       |
| UTF-16 文本             | 由 BOM（`FE FF` / `FF FE`）标明 |

同一个系统里也可能混用：你的 x86 机器是小端，但它收到的 TCP 报文头部是大端，读文件时 PNG 又是大端。**字节序是数据格式的属性，不是机器的属性**。

## 怎么判断当前机器的字节序

最直接的办法：拿一个多字节整数，按字节去看它的内存。

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
  uint32_t value = 0x12345678;
  unsigned char *bytes = (unsigned char *)&value;

  for (int i = 0; i < 4; i++) {
    printf("%02x ", bytes[i]);
  }
  putchar('\n');

  puts(bytes[0] == 0x78 ? "little-endian" : "big-endian");
  return 0;
}
```

把小端机器上会输出：

```text
78 56 34 12
little-endian
```

其他语言里通常有现成的判断方式：

```python
import sys

print(sys.byteorder)  # "little" 或 "big"

value = 0x12345678
print(value.to_bytes(4, "big").hex(" "))     # 12 34 56 78
print(value.to_bytes(4, "little").hex(" "))  # 78 56 34 12
```

C++20 可以直接用 `std::endian::native`，Rust 用 `cfg!(target_endian = "little")` 或 `u32::to_le_bytes()`，Go 用 `binary.LittleEndian` / `binary.BigEndian`。

## 网络字节序：官方指定的大端

TCP/IP 协议栈规定，协议头里的多字节字段统一使用**大端序**，也就是所谓的网络字节序。POSIX 提供了四个转换函数：

```c
#include <arpa/inet.h>

uint16_t host_port = 8080;              // 0x1F90
uint16_t net_port  = htons(host_port);  // 传输时的 16 位值
uint32_t net_addr  = htonl(0x7f000001); // 127.0.0.1
```

在小端机器上，`htons` 会把 `0x1F90` 的字节反过来，让内存里呈现 `1f 90`；接收端再用 `ntohs` 转回主机序。名字里的 `h` 是 host，`n` 是 network，`s` / `l` 是 short / long。

如果跳过转换，直接把 `uint16_t` 塞进发送缓冲区，对端看到的就是 `90 1f`，端口号直接错位。

## 跨平台序列化：别直接 dump 结构体

下面这种写法在单机上跑得很好，跨平台就会出问题：

```c
typedef struct {
  uint32_t id;
  uint16_t port;
  char name[32];
} Record;

fwrite(&record, sizeof(Record), 1, fp);
```

它同时踩了三个坑：

1. **字节序**：换一台不同端序的机器，字段含义就变了。
2. **填充与对齐**：编译器可能在字段之间插入 padding，`sizeof(Record)` 在不同平台、不同编译选项下可能不同。
3. **类型宽度**：`long`、指针宽度在不同平台上不一样。

正确做法是定义明确的线上格式，逐字段按固定宽度和固定字节序编码：

```c
static void put_u32_be(uint8_t *p, uint32_t v) {
  p[0] = (uint8_t)(v >> 24);
  p[1] = (uint8_t)(v >> 16);
  p[2] = (uint8_t)(v >> 8);
  p[3] = (uint8_t)v;
}
```

也可以直接用成熟的序列化方案：protobuf 的 `fixed32` / `fixed64` 在线上固定为小端，varint 按低位优先分组；FlatBuffers、CBOR、MessagePack 也都规定了各自的字节序。**只要格式写清楚了，两端就不需要关心本机是什么端序。**

## 位序不是字节序

字节序讨论的是「字节之间」的顺序。一个字节内部 8 个 bit 的编号和传输顺序，通常由硬件或协议约定，对软件是透明的；左移、右移、掩码都是按数值语义工作的，不会因为大小端而改变结果。

串口、SPI 里说的 MSB-first / LSB-first 是**传输时先发高位还是低位**，那是位序，和内存里的字节序是两件事，不要混为一谈。

## 几个容易踩的坑

- **hexdump 的方向**：`xxd` 从左到右是地址递增。看到 `78 56 34 12` 不代表数值被「反转」了，只是低位字节排在前面。
- **指针强转读缓冲区**：`*(uint32_t *)buf` 可能同时触发未对齐访问和字节序问题。先 `memcpy` 到本地变量，再做 `ntohl`，既安全又清楚。
- **浮点数**：`float` / `double` 同样有字节序。跨端传输时要按位交换，比如先 `memcpy` 到 `uint32_t`，再 `bswap`。
- **位域**：`struct` 里的 bit-field 布局是编译器实现定义的，不要用它来定义跨平台的线上格式。
- **天然安全的部分**：单字节数据、字节数组、UTF-8 文本、文件魔数（如 PNG 的 `89 50 4E 47`）都不涉及字节序。

## 小结

- 字节序只影响多字节数据在内存和字节流里的字节排列。
- x86 和大多数 ARM 是小端，网络协议是大端；文件格式各有规定，不能想当然。
- 写跨平台代码时，明确格式、显式转换、不要直接 dump 结构体，就能避开绝大多数相关 bug。
