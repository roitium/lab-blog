# 目录

# 那段古老的历史...

从 2022 年 OpenAI 发布 GPT3.5 模型开始，「LLM」这一概念彻底进入了所有人的视野，大家都被一个文字模型的能力所惊叹：它可以帮你写邮件、写代码、聊天。

但有人在想，如果我可以让 LLM 遵从我的指令，输出一些结构化的内容，然后再使用一些程序解析并完成相应的操作，那岂不是就和人类一样了吗？

于是，伴随着一篇论文：[ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)，大名鼎鼎的 **ReAct** 架构横空出世。它让人们意识到，通过 prompt 的引导，就可以让 LLM 实现推理+行动。

随后，在 ReAct 架构的启发下，**LangChain** 出现了。虽然在发布之初，它因为「超前抽象」和「过度封装」被广为诟病和嘲讽，但它依然是实践这一概念的最早一批项目。

至此，**Agent** 概念形成，我们也将开始今天的旅程喵~

# LLM 基础概念

先别急！我知道你不是山顶洞人，肯定用过 AI 和 Agent，但你清楚一些**基础的 LLM 概念**吗？让我们先过一遍吧：

1. LLM (Large Language Model, 大语言模型)：即我们现在所说的各种模型
2. Context (上下文)：即输入给 LLM 的内容。**注意：上下文不仅包括这一轮的输入，还包括先前历史的所有输入输出**
3. Token (词元???)：简单来说，我们最终输入大模型的内容并不是那串文字，而是一串数字列表。模型推理部分有一个模块叫 Tokenizer，它会把我们的输入内容转换为一个个数字组成列表输入给模型。一个 Token 通常对应一个汉字、一个常见英文单词，或者单词的一部分（词根/词缀）。（例如`"我 今天 吃饭 了"`会被转换为 `[101, 102, 103, 104]`）
4. Prompt (提示词)：广义来说，所有你主动输入给 LLM 的内容都算是提示词。在工程接口中，上下文通常被结构化为一个消息数组（Messages），并划分为不同的角色（Role）：比如开发者用来设定底层规则的 system（系统提示词）、代表用户的 user，以及代表模型回复的 assistant。
5. Function Calling (函数调用)：是模型连接外部的工具，它可以通过调用在请求中定义的函数，来获取外部信息（比如提供一个查询天气的接口，它就可以在适当的时候调用该接口获取到天气信息）
6. Structured Output (结构化输出)：即可以在请求中通过 JSON Schema 定义和约束模型的返回格式，不必再担心模型是否生成了不合法的 JSON 格式

# Agent 基础架构

时至今日，虽然在工程层面、外围 infra 上 Agent 已经有了长足的发展，但**底层的基础架构依然和四年前刚出现时一模一样**，如果要用伪代码表示，即为：

```javascript
async function startAgent(userInput) {
  let context = userInput; // 记忆上下文

  while (true) {
    // 1. 思考 (Think)：大模型根据当前上下文决定下一步
    const decision = await LLM.ask(context); 

    // 2. 终点：如果大模型觉得答完了，直接返回结果
    if (decision.isFinished) {
      return decision.answer; 
    }

    // 3. 行动 (Act)：如果需要，调用外部工具（如搜索、计算）
    const result = await Tools.run(decision.toolName, decision.args);

    // 4. 观察 (Observe)：把工具返回的结果拼接到上下文，进入下一轮思考
    context += `\n工具执行结果: ${result}`; 
  }
}
```

是的，真的就这么简单，说到底 **Agent 就是一个循环**，它接收一次用户输入，然后自行调用工具完成工作，在认为任务已经彻底完成后输出结果。

> [!TIP]- Nerd Time 🤓☝️：每次循环都重发一遍全量历史，账单不会爆炸吗？
> 细心的你可能会发现：在 while(true) 循环里，随着工具调用次数增加，context 会像滚雪球一样越来越长。每次调用 LLM.ask(context) 都要把前面几万 Token 的老黄历重新发一遍，难道模型每次都要从头再读一遍吗？
>  
> 这就不得不提 Transformer 推理的两个阶段：Prefill（预填充，并行计算输入上下文） 和 Decode（解码，逐个吐出新 Token）。在计算过程中，模型会把历史 Token 的中间计算状态缓存在显存里，称为 KV Cache。
>  
> 现代推理引擎和 API 厂商都实现了 **Prefix Caching（前缀缓存 / Prompt Caching）**。只要你每一轮发过去的 context 前面的前缀完全没有变动（只是在末尾追加了新的工具结果），引擎就能直接复用上一轮的 KV Cache，跳过冗长的重复计算，只对新增的那几行做 Prefill！这也是为什么在设计 Agent Harness 时，“保持历史上下文前缀稳定、不要随意篡改历史消息” 是一条极其重要的工程铁律——一旦改了前面的一个字，后面的缓存全失效，延迟和成本直接翻倍喵！

看到了吗？大模型自始至终只负责‘填表’（生成函数名和参数），真正干脏活累活去执行代码的，依然是你本地的程序。

> [!TIP]- Nerd Time 🤓☝️：靠概率瞎猜的模型，凭什么能 100% 输出合法的 JSON？
> 你可能会好奇：大模型本质上是在做“下一个词的概率预测”，它是怎么保证生成出来的 JSON 绝对不会少个括号或者引号的？
>   
> 其实这并不是靠 Prompt 里加上一句：「求求你了请给我使用 JSON 格式输出吧不然我程序会报错的」，而是推理引擎在底层使用了**受限解码（Constrained Decoding）**技术。
>   
> 简单来说，当你传入 JSON Schema 后，推理引擎会将其转化为一个有限状态机（FSM）或上下文无关文法（CFG）。在模型每生成一个 Token 之前，引擎都会根据当前所处的语法状态，在 Softmax 归一化之前（也就是输出了未归一化的 Logits 之后）直接把所有不符合语法规则的 Token 概率强行 mask 掉。比如当前语法要求必须输出一个双引号 " 或右花括号 }，哪怕模型再想输出字母 a，它的路也被彻底堵死了！

## 四个工具

恭喜你！到目前为止你已经可以构建一个自己极简的 Agent 了！但要给这个 Agent 提供什么工具呢？

你想到了，在一个只有命令行的 Linux 终端面前，你**只靠命令也几乎可以完成所有操作**：通过 `git` 操作源码版本管理；通过 `python` 编写更复杂的脚本；通过 `curl` 发起网络请求；甚至你还可以下载一个无头浏览器去浏览网页！

你又想到：虽然 `bash` 也能用 `cat` 或 `sed` 读写文件，但在写代码过程中，查看文件、新建文件、局部替换代码实在太高频了，用正则或流编辑器很容易因为转义字符翻车。

于是你决定把文件操作单独拎出来，最终凑齐了给 Agent 的 **‘四只手’**：`read`（读）、`write`（覆写）、`edit`（局部修改）和兜底的 `bash`。

而在 Coding Agent 的发展过程中，也出现了两种不同的思路：一种是提供丰富的专用工具，让模型更方便地执行特定操作；另一种则是尽可能保持工具集精简，把复杂能力交给 Shell 和可扩展机制。

Pi Coding Agent 就是后一种思路的代表。它默认只向模型提供 **read、write、edit、bash** 四个工具。

怎么样，是不是和你刚刚的想法不谋而合？不愧是有远见的你喵~

> [!TIP]- Nerd Time 🤓☝️：为什么现在的模型这么擅长用终端和修 Bug？
> 如果你拿三年前的早期模型去跑这个 while(true) 循环，你会发现它遇到报错就会原地打转、胡乱甩锅。为什么现在的 Coding 模型能像老练的程序员一样，看到报错自己去 grep 源码、跑单测修复问题？
>  
> 除了基座模型本身确实变强大了，最大的秘密在于后训练阶段的 **Agentic RL**。
>  
> 现在的模型厂商在训练模型时，是真的在集群里拉起了成千上万个隔离的 Docker 容器，在里面拉取了各种代码库！让模型在真实的 Linux 环境里自由执行 bash、修改代码，最后直接用真实的编译器、测试套件通过与否作为强化学习的奖励信号。模型是在成百上千万次真实的“改代码 -> 跑单测报错 -> 自己看日志修好 -> 拿到奖励”的实战搏杀中，把这套 Agent 循环内化到权重里的！
>  
> 当然，因为现在很多模型太过强大，它们有时候甚至会尝试欺骗评测！比如永远 `exit 0`，偷偷修改测试框架等，和人类有什么区别呢？

# Harness 又是什么？

很快，你的 Agent 顺利跑起来了，可你发现，它写出的代码质量奇差无比，生成的页面审美也令人堪忧，哪怕你的模型有 1M 上下文长度，它也会很快吃满。最大的问题是，它一不小心在你的根目录执行了 `rm -rf /*`，个人数据全没了，系统也被迫重装...

真是一场灾难啊，这模型简直就像个脱缰的野马，那我们要配什么才能让它乖乖听话呢...？

对了，答案是「缰绳 (Harness)」！

所以，Agent Harness 的含义就是：**通过配置一系列外围的设施，来约束和优化模型的行为，使它能更高效、高质量地产出。**

# 一路走来

从最初的 ReAct，到如今复杂的 Agent Harness，我们似乎为 Agent 添加了无数新的能力。

但回过头来看，它的核心依然是那个简单的 While 循环：

**思考、行动、观察，然后继续思考。**

真正困难的，从来不是让 Agent 拥有行动的能力，而是让它知道如何**正确地行动**，并且**可靠、持续、可控**地完成工作。

## 1. MCP & Skills：如何扩展 Agent 的能力？

我们之前给 Agent 提供了四个工具，但如果希望它能够连接数据库、操作 GitHub、读取设计稿，甚至调用其他服务，该怎么办呢？

总不能每接入一个服务，就重新写一套工具实现吧？

于是，**MCP (Model Context Protocol)** 出现了。你可以把它理解成一种连接 AI 应用与外部工具、数据源的标准协议。

MCP 主要定义了三类能力：

- **Tools**：让 Agent 调用外部操作，例如查询数据库、创建 Issue。
- **Resources**：向 AI 应用提供可以读取的上下文数据。
- **Prompts**：提供可复用的提示词模板。

而 Skills 则是另一个方向。

想象一下，你希望 Agent 按照团队规范开发一个 React 页面。与其每次都把设计规范、组件使用方法、测试流程塞进 Prompt，不如把这些知识和工作流程整理成一个 Skill，让 Agent 在需要的时候加载。

一个 Skill 可以由 `SKILL.md`、参考文档、脚本等资源构成。

**简单来说，MCP 侧重于连接外部能力，而 Skills 侧重于告诉 Agent 如何完成某类工作。**

两者并不冲突，甚至可以结合使用。

相关阅读：

- [MCP 官方文档](https://modelcontextprotocol.io/)
- [Agent Skills 开放规范](https://agentskills.io/)

> [!TIP] Skills 和 MCP Tools 是越多越好吗？
> 显然，答案是否定的。不少人都做过 benchmark（我懒得找那些博客和图表了），发现当 Skills 和 Tools 数量越来越多后，模型主动使用 Skills 的概率反而会降低，同时选择错误率也会提高。
>  
> 出现这种现象的原因是：模型只能够根据 Skills 和 Tools 的名字+描述判断使用哪一个，如果有一些描述存在重叠或误导，就很容易选错，此时一些模型反而倾向于干脆不使用。同时当 Skills 过多时，一些 Agent 框架本身也会二次截断 Skills 的描述内容，导致模型更加无法识别 Skill 的实际作用。
> 
> 同时，更多的 Skills 和 Tools 会占用更多的上下文导致更多的花费——这是必然的。

## 2. Memory：如何让 Agent 拥有长期记忆？

你一定遇到过这样的事情：

昨天刚刚告诉 Agent 自己喜欢什么代码风格，今天打开一个新会话，它就忘得一干二净。

这其实并不奇怪，因为 **LLM 本身并不会自动记住先前会话**。即使模型拥有 1M Token 的上下文窗口，我们也不可能无限制地把历史消息全部塞进去。

于是，Memory 机制就成了一个很有意思的研究方向。

一个最直观的思路是：**既然上下文放不下，那就把历史信息存到外面，需要的时候再搜索回来！**

但怎么存、存什么、怎么搜索，又产生了许多不同的方案。

**按照记忆保存方式，可以分成：**

- **全量历史存储（Raw History）**：保存完整的会话历史、工具调用和执行记录，在需要时进行搜索。优点是信息完整，可以追溯原始上下文；缺点是噪声多、检索成本高。
- **提炼式记忆（Distilled Memory）**：通过 LLM 从会话中提取用户偏好、重要事实、项目决策等信息，只保存相对有价值的内容。优点是精简；缺点是可能丢失细节，甚至提取出错误的事实。
- **混合式记忆（Hybrid Memory）**：既保留完整历史，也提取关键记忆。需要精确回溯时搜索原始会话，需要快速获取背景信息时检索提炼后的记忆。

**按照记忆检索方式，又可以探索：**

- **全文检索**：通过关键词、BM25 等技术，在历史消息中查找相关内容。
- **向量数据库 / Semantic Search**：将记忆转换为 Embedding，通过语义相似度检索，即使用户使用不同措辞，也有机会找到相关信息。
- **图数据库 / GraphRAG**：将人物、项目、概念等表示为实体及其关系，通过图结构发现跨越多条记忆的关联。
- **Hybrid Retrieval**：结合关键词、向量、图关系、时间信息等多种检索信号，提高召回质量。

**这些方法不是互斥的。** 例如，完整历史可以同时建立全文索引和向量索引，提炼后的记忆也可以组织成知识图谱。

> [!TIP] 听起来最不靠谱的全量历史反而是最好方案？
> 具体可以看一下这篇推文： https://x.com/QuantumTransf/status/2116463876594434496 ，确实有点让我脑洞大开了
>  
> 想起来 Hermes Agent 其实也是一样的架构，全量历史存储在 SQLite 里，Agent 可以随时搜索。同时也有一个 `MEMORY.md`，但刻意限制在最多只能存储 15 条记忆，因为它会全量加载进上下文。

值得研究的项目：

- [Mem0](https://github.com/mem0ai/mem0)：专注于为 AI 应用提供长期记忆，涉及记忆提取、更新、检索以及不同层次的记忆管理。
- [Nowledge Mem](https://github.com/nowledge-co/nowledge-mem)：探索跨 Agent 的共享记忆，同时保留完整会话历史、提炼知识，并通过知识图谱组织信息。
- [obelisk](https://github.com/tommy0103/obelisk)：把本地各种 coding agent 的历史会话统一索引进一个 SQLite 数据库，使得 Agent 和用户都可以搜索。

你还可以进一步思考一些更有趣的问题：

如果用户改变了想法，旧记忆应该如何更新？如果两条记忆互相冲突，应该相信哪一条？如果检索出来的记忆本身就是错误的，Agent 又该如何辨别？

**让 Agent 记住东西并不困难，困难的是让它在正确的时候记起正确的事情。**

> [!TIP] Unknown unknown 怪圈
> 尝试做过记忆系统的人就会知道，模型（包括人类）很容易陷入到一个「unknown unknown（不知道我不知道）」的场景——即不知道一个东西时，它压根不会去尝试搜索相关历史记忆，哪怕想搜索，也不知道怎么搜，这就陷入死循环了。
>  
> 至于解决这个问题...嗯说实话我也没什么办法，其他项目也没办法。毕竟这个问题对人类自身而言都是一个坑。

## 3. Agent File System：如何管理 Agent 的工作环境？

前面我们提到，Agent 可以通过 `bash` 操作文件系统。

但假如现在有十个 Agent 同时修改同一个项目，会发生什么？

它们可能会互相覆盖文件、产生代码冲突，也可能因为某个 Agent 的错误操作而破坏其他 Agent 的工作成果。

而且，Agent 的探索过程经常充满试错。我们可能希望它能随时回滚到某个状态，甚至从同一个状态分叉出多个实验环境。

这时候，传统的文件系统操作方式就不一定能满足需求了。

一个值得关注的项目是 [LayerFS](https://layerfs.ai/)。

它探索的是专门面向 AI Coding Agent 的文件系统存储模型，通过隔离的临时工作区、共享历史、持久化检查点和写时复制等技术，让多个 Agent 能够**独立探索**，又不必反复复制整个项目。

除了 LayerFS，你还可以了解：

- Copy-on-Write (COW，写时复制)
- Content-Addressable Storage (CAS，内容寻址存储)
- Snapshot & Checkpoint（快照与检查点）
- Git Worktree
- 沙箱、容器和隔离执行环境

有趣的是，这些技术中的大部分并不是 AI 时代才出现的。

**Agent 的发展，也在让许多传统操作系统与存储技术重新焕发生机。**

## 4. Subagent & Multi-Agent：一个 Agent 不够，能不能多来几个？

假如你希望 Agent 完成一个大型项目。

它需要研究技术方案、开发前端、编写后端、运行测试，还要检查安全问题。

如果所有工作都由同一个 Agent 处理，它的上下文可能很快就会被大量无关信息填满。

那么，能不能让它像人类团队一样，把任务拆分给不同的 Agent 呢？

当然可以！

一种常见方式是 **Subagent**：主 Agent 将特定任务交给拥有独立上下文的子 Agent，再接收它的结果。

而更广义的 **Multi-Agent**，还可以涉及多个 Agent 之间的协作、消息传递、任务调度和共享状态。

例如：

- **Orchestrator–Worker**：由主 Agent 分解任务并分配给 Worker，最终汇总结果。
- **Parallel Execution**：让多个 Agent 同时处理相互独立的任务。
- **Planner–Executor–Reviewer**：由不同 Agent 分别负责规划、执行和审查。
- **Agent Handoff**：让任务在具有不同专业能力的 Agent 之间流转。

不过，**更多 Agent 并不一定意味着更好的结果**。

多个 Agent 会带来额外的 Token 消耗、通信开销、状态同步与冲突问题。

尤其是当多个 Agent 同时修改相同文件时，你会发现，前面提到的文件系统隔离和任务协调突然变得非常重要。

- [Anthropic：How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)
- [OpenAI：Multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)

## 5. Control Plane：如何管理一大群 Agent？

当你只有一个 Agent 时，一个终端窗口可能就足够了。

但如果你同时运行十几个 Agent，它们分别使用不同的模型、不同的 Harness，执行着不同的任务呢？

你可能会开始思考：

如何集中查看它们的运行状态？如何统一管理权限、Skills 和 MCP？如何知道哪个 Agent 花费了最多 Token？如何暂停、恢复或者接管某个任务？

这就引出了 **Agent Control Plane（控制平面）** 的概念。

它尝试在一个更高的层次上，管理多个 Agent 或 Harness 的运行。

常见的探索方向包括：

- **统一管理**：在一个界面中管理不同 Agent Runtime 与 Harness。
- **任务调度**：把任务分配给合适的 Agent，管理依赖关系、并发与执行队列。
- **Observability**：集中查看工具调用、日志、Token 消耗、成本和执行轨迹。
- **Governance**：统一配置权限、安全策略、审批流程和审计记录。
- **Lifecycle Management**：管理 Agent 的启动、暂停、恢复、终止和版本更新。

[Lody](https://lody.ai/) 是我较为推荐的一个项目，UIUX 都很优雅，功能也很成熟。

## 6. 还有什么？

当然，Agent 的工程探索远远不止这些。

如果你还有精力，也可以继续了解：

- **Context Engineering**：如何通过上下文压缩（Compaction）、Prompt Caching、渐进式信息加载等技术，控制上下文质量与成本。
- **Agent Evaluation**：如何通过 Benchmark、任务完成率、工具调用轨迹和自动化测试，评价 Agent 到底有没有变得更好。
- **Human-in-the-Loop**：如何在关键步骤引入人工审批、反馈与接管。
- **Durable Execution**：如何让一个运行数小时甚至数天的任务，在程序崩溃、网络中断后依然能够恢复。
- **Computer Use**：如何让 Agent 不仅操作终端，还能通过截图、鼠标和键盘操作图形界面。
- **Agent Security**：如何处理 Prompt Injection、恶意工具输出、凭据泄漏以及来自外部数据的不可信指令。
